CLASS MODE / PERIOD 01교수자 이론과 설명

학생은 프로젝트를 제작하지 않습니다. 교수자의 상태 도표와 Unity 화면을 관찰하고, 사건 뒤에 어떤 값과 화면이 바뀔지 먼저 예측합니다. 실제 연결은 2교시 시연 뒤 3교시 개인 실습에서 수행합니다.

WEEK 07 / GAME LOOP

목표와 끝을 이해합니다

점수와 시간이 보이고, 성공과 실패가 구분되며, 버튼으로 처음 상태에서 다시 시작할 수 있습니다.

조작 가능한 장면+상태와 피드백=반복 가능한 게임 루프
교수자 질문

“수집물을 모두 먹었는데 아무 일도 일어나지 않는다면, 코드가 실패한 것일까요, 피드백이 빠진 것일까요?” 먼저 학생의 답을 받은 뒤 데이터 변경, 판정, 표현을 따로 확인해야 한다고 연결합니다.

하나의 기준

게임의 사실은 UI 글자 안에 있지 않습니다

화면은 결과를 보여 주는 출력입니다. 실제 점수와 남은 시간, 현재 상태는 코드의 데이터가 기억하고 있어야 합니다.

  1. 01 / EVENT사건 발생

    Player가 수집물에 닿거나 시간이 흐릅니다.

  2. 02 / DATA값 변경

    score가 늘고 timeRemaining이 줄어듭니다.

  3. 03 / RULE조건 판정

    목표 점수와 시간 종료 조건을 검사합니다.

  4. 04 / STATE상태 전환

    Playing에서 Won 또는 Lost로 이동합니다.

  5. 05 / FEEDBACK표현 갱신

    HUD, 결과 화면과 효과음이 상태를 알립니다.

DATAscore

현재 모은 수를 저장하는 정수입니다.

DATAtimeRemaining

현재 남은 시간을 저장하는 실수입니다.

STATEcurrentState

지금 허용할 게임 규칙을 선택합니다.

OUTPUTscoreText.text

저장된 값을 사람이 읽는 글자로 보여 줍니다.

한 곳에서만 진실을 관리하기 성공 여부를 확인하려고 화면의 “3 / 3” 문자열을 다시 읽지 않습니다. score와 targetScore를 비교하고, 그 결과를 UI에 씁니다.

상태 모델

상태는 지금 허용되는 규칙의 묶음입니다

상태 이름은 화면 제목이 아닙니다. 입력, 시간, 수집, 패널과 재시작 중 무엇이 작동해야 하는지를 한 단어로 묶은 규칙입니다.

  1. STATE 01Ready

    시작 패널이 보입니다. 타이머와 플레이는 아직 멈춰 있습니다.

  2. STATE 02Playing

    입력, 물리, 수집과 타이머가 작동합니다.

  3. STATE 03AWon

    목표 점수에 도달했습니다. 성공 화면을 보여 줍니다.

  4. STATE 03BLost

    시간이 먼저 끝났습니다. 실패 화면을 보여 줍니다.

판정 순서 질문

남은 시간이 0.02초일 때 마지막 수집물을 얻었다면 어떤 결과가 되어야 할까요? 이 수업에서는 먼저 들어온 사건을 한 번만 처리하도록 설계합니다. 상태가 Won으로 바뀐 뒤에는 Lost 판정과 추가 점수가 무시되어야 합니다.

화면 구조

계속 보는 정보와 잠깐 보는 화면을 나눕니다

모든 정보를 한 Panel에 넣으면 상태 전환 때 무엇을 숨겨야 하는지 복잡해집니다. 역할과 표시 시점을 기준으로 계층을 나눕니다.

HUD / WHILE PLAYING

플레이 중 판단을 돕는 정보

현재 점수, 목표 점수와 남은 시간을 화면 가장자리에 작고 지속적으로 보여 줍니다. 플레이 공간을 가리지 않아야 합니다.

사건과 피드백

한 사건은 여러 피드백을 함께 일으킵니다

수집물은 스스로 점수 글자를 고치고 성공 화면을 켜지 않습니다. 사건을 알리고, 상태를 관리하는 한 곳이 데이터와 표현을 함께 조정합니다.

AudioSource를 보는 관점

AudioSource는 소리의 출발점이고 AudioClip은 재생할 소리 데이터입니다. 짧은 수집, 성공과 실패 효과음은 하나의 AudioSource에서 PlayOneShot으로 재생할 수 있습니다. 소리는 사건의 원인이 아니라 결과를 강화하는 피드백입니다.

자주 생기는 오류

기능이 늘어날수록 책임을 한곳에 모읍니다

처음에는 어디에 코드를 써도 작동해 보이지만, 성공과 실패가 추가되면 서로 다른 Script가 같은 값을 바꾸기 시작합니다.

점수를 UI Text에서 다시 읽습니다

화면 문자열은 표현 형식이 바뀌기 쉽습니다. score 정수를 진실로 유지하고, scoreText.text에는 그 값을 사람이 읽는 모양으로 써 줍니다.

isWin, isLose, isPlaying을 따로 둡니다

여러 bool이 동시에 true가 되는 모순이 생길 수 있습니다. 한 번에 하나만 가질 수 있는 GameState enum으로 현재 상태를 표현합니다.

각 수집물이 성공 화면을 직접 켭니다

수집물은 접촉 사건만 전달합니다. 전체 목표 점수와 종료 조건을 아는 GameManager가 점수를 올리고 성공 여부를 판단합니다.

결과 화면 뒤에서도 점수가 계속 오릅니다

AddScore 시작에서 현재 상태가 Playing인지 검사합니다. Won이나 Lost라면 곧바로 return해 사건을 무시합니다.

시간이 0 아래로 계속 내려갑니다

Mathf.Max(0f, ...)로 표시값을 0에 고정하고, Playing에서만 시간을 줄입니다. 종료 전환은 한 번만 실행합니다.

UI 크기가 화면 비율마다 크게 달라집니다

Canvas Scaler와 Rect Transform Anchor를 함께 확인합니다. 화면 중앙, 모서리 등 요소의 역할에 맞는 기준 위치를 먼저 정합니다.

회수 질문

화면을 덮고 상태 흐름을 복원합니다

먼저 자신의 말로 답한 뒤 펼쳐 확인합니다. 메뉴 이름보다 원인, 상태와 출력의 순서를 설명하는 것이 중요합니다.

Q1. 점수 Text가 게임의 실제 점수가 아닌 이유는?

Text는 score를 사람이 읽도록 보여 주는 출력이기 때문입니다. 게임 규칙은 정수 데이터인 score와 targetScore를 비교해야 합니다.

Q2. Playing 상태에서만 해야 하는 일은?

입력과 물리 이동, 수집 처리, 타이머 감소와 성공·실패 판정입니다. Ready, Won과 Lost에서는 이 규칙을 멈추거나 무시합니다.

Q3. HUD와 Result Panel의 차이는?

HUD는 플레이 중 계속 참고하는 점수와 시간입니다. Result Panel은 Won 또는 Lost로 상태가 바뀐 순간 중앙에 나타나 결과와 다음 행동을 알립니다.

Q4. 수집 사건 뒤의 올바른 순서는?

Playing인지 확인하고 점수를 올립니다. HUD와 수집 효과음을 갱신한 뒤 목표 점수를 검사하고, 도달했다면 Won으로 한 번만 전환합니다.
