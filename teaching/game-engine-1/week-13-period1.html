CLASS MODE / PERIOD 01교수자 이론과 설명

학생은 프로젝트를 제작하지 않습니다. 교수자가 같은 사건에 서로 다른 UI와 소리를 적용한 예시를 재생하면, 학생은 먼저 무엇이 전달되었는지 예측하고 근거를 말합니다. Unity 설정과 생성 도구 조작은 개념을 설명하기 위한 화면 확인에만 사용하며 실제 통합과 수정은 3교시 개인 실습에서 수행합니다.

“반짝임과 효과음이 동시에 나오면 좋은 피드백일까요?” 먼저 답을 받은 뒤, 두 신호가 같은 사건을 가리키는지, 다른 사건과 구분되는지, 실제 화면에서 놓치지 않는지까지 통과해야 한다고 연결합니다.

소리 파일, 재생 장치와 전체 규칙을 구분합니다

효과음 문제를 모두 파일 탓으로 돌리지 않습니다. 원본, 재생 Component, 그룹 정책과 호출 시점을 나누면 수정 지점을 빠르게 찾을 수 있습니다.

PLAY

하나의 clip을 이어 재생

AudioSource.Play()는 Source에 지정된 clip을 재생합니다. 배경음처럼 한 clip의 시작·정지와 반복을 관리할 때 이해하기 쉽습니다.

PLAY ONE SHOT

짧은 사건을 겹쳐 재생

PlayOneShot(clip, volumeScale)은 지정한 clip을 한 번 재생하며 이미 재생 중인 OneShot을 자동으로 취소하지 않습니다. 같은 사건이 매 frame 호출되지 않도록 조건을 먼저 확인합니다.

  1. S01 / START시작이 즉시 읽힙니다

    앞부분의 긴 무음을 trim하여 사건과 소리 사이의 지연을 줄입니다.

  2. S02 / SHAPE끝이 정리됩니다

    갑자기 잘린 꼬리와 click noise를 피하도록 짧은 fade를 확인합니다.

  3. S03 / ROLE서로 구분됩니다

    수집·피해·성공을 음높이 하나가 아니라 길이·질감·윤곽까지 다르게 설계합니다.

  4. S04 / LEVEL균형이 유지됩니다

    한 소리만 과도하게 크거나 여러 번 겹쳐 찢어지는지 실제 게임 루프에서 듣습니다.

  5. S05 / CALL사건당 한 번입니다

    Console과 재생 횟수로 중복 호출을 확인하고, 효과음 자체보다 조건을 먼저 고칩니다.

생성 도구는 후보를 만들고, 게임 안 검사가 완성합니다

Unity의 Sound Generator는 자연어 설명과 선택적 참조로 효과음·환경음 후보를 만들고 WAV로 프로젝트에 가져오는 프로토타이핑 도구입니다. 현재 음악 생성 도구로 가정하지 않습니다.

  1. 01

    역할과 길이를 먼저 적습니다

    “숲 게임의 작은 수집물을 획득할 때 나는 짧고 밝은 확인음, 시작 지연 없음, 사람 목소리와 멜로디 없음”처럼 사건·질감·길이·제외 조건을 씁니다.

    통과 프롬프트만 읽어도 수집·피해·성공 중 어느 역할인지 구분됩니다.

  2. 02

    소수 후보를 비교합니다

    생성 횟수보다 실제 게임의 다른 소리와 구분되는지를 봅니다. 가장 화려한 결과가 아니라 가장 빠르게 의미가 읽히는 결과를 선택합니다.

    통과 후보 선택 이유를 길이·시작·질감·다른 사건과의 차이로 설명합니다.

  3. 03

    Trim과 envelope를 확인합니다

    시작과 끝의 무음, 갑작스러운 절단, 불필요한 잔향을 정리하고 원본과 수정본을 구분합니다.

    통과 사건 직후 소리가 시작되고 끝부분에 click이나 잘린 느낌이 없습니다.

  4. 04

    출처와 사용 여부를 기록합니다

    도구·모델 또는 서비스, prompt, reference 권리, 사람의 수정과 최종 채택 여부를 제작 로그에 남깁니다.

    통과 생성 기능을 사용할 수 없어도 허용된 기존 효과음이나 수업용 placeholder로 같은 피드백 계약을 검증할 수 있습니다.

ACCESS RULE계정·credit·특정 생성 도구는 평가 조건이 아닙니다. AI 효과음, 사용 허가된 기존 효과음, 수업용 placeholder 모두 같은 사건·구분·음량·기록 기준으로 평가합니다.

플레이어가 묻는 순서대로 화면을 정리합니다

UI는 정보를 많이 보여 주는 판이 아닙니다. 지금 필요한 질문에 먼저 답하고, 상태가 바뀌면 그 답도 함께 갱신되는 인터페이스입니다.

  1. 01 / GOAL무엇을 해야 하나

    이번 판의 목표를 처음 10초 안에 찾을 수 있습니다.

  2. 02 / CURRENT지금 어떤 상태인가

    수집 수, 남은 시간, 체력처럼 행동의 결과를 확인합니다.

  3. 03 / NEXT다음에 무엇을 하나

    목표까지 부족한 조건이나 진행 방향을 과도한 설명 없이 제시합니다.

  4. 04 / RESULT무엇이 끝났나

    성공·실패를 같은 화면처럼 보이지 않게 구분합니다.

  5. 05 / RECOVER어떻게 다시 하나

    재시작 또는 다음 단계의 조작을 결과와 가까운 곳에서 찾습니다.

10초 검사

샘플 게임 화면을 10초만 보여 준 뒤 “목표, 현재 상태, 다음 행동은 무엇이었나요?”를 묻습니다. 설명을 더하기 전에 위치·크기·문자·형태의 위계가 답을 만들었는지 확인합니다.

같은 정보를 두 번 말하되, 혼란은 두 배로 만들지 않습니다

중복 표현은 효과를 겹치는 일이 아니라 서로 다른 감각이 같은 의미를 보완하게 만드는 설계입니다.

GOOD REDUNDANCY

두 신호가 같은 사건을 가리킵니다

피해 순간 체력 숫자와 아이콘이 변하고 구분되는 경고음이 한 번 납니다. 소리를 끄거나 색을 빼도 피해 사실은 남습니다.

NOISE

여러 효과가 서로 다른 말을 합니다

수집 순간 화면 전체가 붉어지고 실패음과 비슷한 소리가 반복되면 정보량은 늘지만 의미는 흐려집니다.

ACCESSIBILITY FLOOR

핵심 조작과 상태 설명을 소리, 색, 위치 또는 모양 하나에만 맡기지 않습니다. 작은 게임의 최소 기준은 음소거 상태와 회색조 화면에서도 목표·피해·성공·재시작을 구분할 수 있는 것입니다.

효과를 더하기 전에 원인을 분리합니다

아래 증상은 3교시에서 자주 만나는 문제입니다. 먼저 사건·호출·원본·재생·표시 중 어느 층의 문제인지 구분합니다.

한 번 수집했는데 효과음이 여러 번 납니다

clip을 다시 만들기 전에 사건 호출 횟수를 봅니다. Update()나 Trigger 체류 중 매 frame 호출되는지, 수집물 비활성화와 상태 변경이 한 번만 일어나는지 확인합니다.

효과음이 늦게 들립니다

원본 앞부분의 무음, 호출 시점, 로딩과 AudioSource 설정을 분리합니다. 파형의 실제 시작을 먼저 trim한 뒤 같은 사건으로 다시 비교합니다.

UI는 예쁘지만 목표를 찾기 어렵습니다

장식을 추가하기보다 목표·현재·다음의 순서를 다시 정합니다. 10초 검사에서 회수되지 않은 정보는 위치, 크기, 문자와 대비부터 고칩니다.

성공과 실패가 색으로만 구분됩니다

서로 다른 제목, 아이콘 실루엣, 화면 구조와 행동 버튼을 추가합니다. 색은 보조 단서로 유지하되 유일한 단서로 사용하지 않습니다.

생성된 UI를 넣자 Button이 작동하지 않습니다

Canvas와 Button을 새로 만들지 말고 기존 Image의 Source Image 또는 Texture 참조만 교체했는지 확인합니다. Raycast Target, Button On Click과 hierarchy를 baseline과 비교합니다.

배경음 때문에 핵심 효과음이 묻힙니다

SFX 파일만 키우기 전에 Music과 SFX를 Mixer group으로 나누고 상대 음량을 비교합니다. 여러 소리가 겹치는 실제 플레이 순간에 다시 듣습니다.

설명 없이 다섯 문장으로 회수합니다

정답을 바로 보여 주지 않습니다. 학생이 먼저 말한 뒤 피드백 사슬과 계약표를 다시 열어 빠진 항목만 보완합니다.
