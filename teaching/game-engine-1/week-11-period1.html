학생은 프로젝트를 제작하지 않습니다. 교수자가 같은 요청을 Ask, Plan, Agent로 바꾸어 보여 주고 학생은 각 모드가 읽는 것, 제안하는 것과 실제로 바꾸는 것을 구분합니다. 개인 프로젝트의 변경은 3교시 승인 이후에만 시작합니다.

문제 정의 예시

현재 Week10_AssetIntegration은 Ready, Playing, Won, Lost와 30초 타이머가 정상입니다. Player가 새 TimeBonus Trigger에 처음 닿으면 Playing에서만 남은 시간이 5초 늘고 30초를 넘지 않게 하려 합니다. 수정은 GameManager.cs와 새 TimeBonus.cs로 제한합니다. Scene, Prefab, Package와 ProjectSettings는 바꾸지 않습니다. 먼저 현재 구조와 이 목표 사이의 필요한 변경점만 읽기 전용으로 설명해 주세요.

그럴듯함과 프로젝트의 사실을 분리합니다

hallucination은 엉뚱한 문장만 뜻하지 않습니다. 실제 프로젝트에 없는 이름, 버전과 연결을 확신하는 답도 포함합니다.

  • 01
    존재하지 않는 이름을 전제로 함

    GameManager.Instance가 없는데 singleton처럼 호출하거나 실제 변수와 다른 remainingTime을 사용합니다. 먼저 현재 파일에서 정확한 이름을 확인합니다.

  • 02
    Unity 버전과 패키지를 추측함

    설치되지 않은 package API나 다른 Unity 버전의 메뉴를 제안할 수 있습니다. 설치된 버전과 Package Manager를 실제로 확인합니다.

  • 03
    숨은 의존성을 만듦

    새 Script가 Tag, Layer, Collider, Inspector 참조를 요구하면서 설명하지 않을 수 있습니다. 코드 밖의 수동 연결을 Plan에 포함합니다.

  • 04
    요청하지 않은 정리를 함께 함

    함수명 변경, 파일 이동과 리팩터링이 섞이면 diff가 커지고 기존 Inspector 연결을 잃을 수 있습니다. 기능 하나와 정리 작업을 분리합니다.

  • 05
    실행하지 않고 완료를 선언함

    컴파일 가능성은 플레이 성공과 다릅니다. Agent의 “완료”는 주장이고 Console, Inspector와 Play Mode가 증거입니다.

판정 문장

“AI가 맞는 것 같다” 대신 “현재 파일에서 이름을 확인했다”, “diff에 두 파일만 있다”, “T01부터 T08까지 같은 조건에서 통과했다”처럼 다시 관찰할 수 있는 문장을 사용합니다.

권한은 기능보다 작거나 같아야 합니다

Agent가 작성하는 구현 코드는 두 C# 파일이면 충분합니다. Plan 문서, Unity가 만드는 메타데이터와 학생이 저장하는 Scene은 구현 코드와 구분해 기록합니다.

승인 전 확인 문장

실행하지 말고 계획만 보여 주세요. 각 단계에 예상 변경 파일, 변경할 함수, Scene에서 사람이 직접 할 일, 실패 가능성, 실행할 테스트를 적으세요. 두 C# 파일 밖의 변경이 필요하다면 그 이유만 보고하고 멈추세요.

코드보다 먼저 파일 목록을 읽습니다

diff는 AI가 한 일을 기억에 의존하지 않고 변경 전후로 비교하는 기록입니다. 줄 수보다 변화의 책임과 부작용을 봅니다.

  1. 01

    변경 파일 분류

    git status --short 또는 changed files에서 Agent 구현 코드, Plan 문서, Unity 생성 .meta, 학생이 저장한 Scene을 먼저 나눕니다.

    중단 세 번째 구현 파일, 예상하지 않은 Prefab, package manifest나 설정이 보입니다.

  2. 02

    공개 표면

    새 public 메서드가 필요한 호출만 열어 주는지, 기존 함수명과 serialized field를 불필요하게 바꾸지 않았는지 봅니다.

    질문 이 public 메서드를 누가, 언제 호출합니까?

  3. 03

    상태 문과 값의 경계

    Playing이 아닐 때 return하는지, 5초가 양수인지, 결과가 30초 상한을 넘지 않는지 봅니다.

    질문 28초에서 보너스를 얻으면 정확히 몇 초가 됩니까?

  4. 04

    사건의 횟수

    Trigger가 같은 오브젝트에 여러 번 들어와도 보너스를 한 번만 지급한 뒤 비활성화되는지 봅니다.

    질문 상태 기록과 보너스 지급 중 무엇을 먼저 해야 합니까?

  5. 05

    회귀 가능성

    기존 Update, AddScore, FinishRound와 Restart의 흐름이 그대로 남았는지 확인합니다.

    증거 새 기능뿐 아니라 성공, 실패와 두 번의 재시작도 실행합니다.

“Agent가 완료했다”는 완료 조건이 아닙니다

완료는 생성된 코드가 아니라 독립적으로 다시 확인할 수 있는 다섯 종류의 증거가 함께 있을 때 성립합니다.

설명을 덮고 다섯 문장으로 회수합니다

정답을 보기 전에 소리 내어 답합니다. 답이 모호하면 해당 절로 돌아가 근거가 되는 실제 파일과 테스트를 함께 찾습니다.

Ask와 Plan은 둘 다 프로젝트를 바꾸지 않습니다. 차이는 무엇입니까?

Ask는 현재 구조와 개념을 설명하는 데 적합합니다. Plan은 목표를 여러 단계로 나누고 예상 파일, 순서, 위험과 테스트를 실행 전에 제안합니다.

시간 보너스 기능에 Full autonomy가 필요하지 않은 이유는 무엇입니까?

필요한 코드 변경은 기존 GameManager 한 파일과 새 TimeBonus 한 파일뿐입니다. Scene 연결은 학생이 Inspector에서 직접 할 수 있으므로 더 넓은 쓰기 권한은 목표보다 큽니다.

Agent가 세 번째 구현 파일을 바꾸려 하면 어떻게 합니까?

즉시 중단하고 변경을 적용하지 않습니다. 단, Plan 문서, Unity 생성 .meta, 수동 저장 Scene은 작성 주체를 확인해 예상 지원 산출물로 분류합니다.

diff에서 가장 먼저 보는 것은 무엇입니까?

코드 줄이 아니라 변경된 파일 목록과 작성 주체입니다. 구현 코드가 허용한 두 파일인지 확인한 뒤 공개 메서드, 상태 문, 경계와 부작용을 읽습니다.

완료를 증명하는 다섯 증거는 무엇입니까?

허용 범위의 diff, Console Error 0, 새 행동의 Play Mode 결과, 기존 기능 회귀 테스트와 학생의 코드 구술입니다.

수업 중 확인할 공식 자료

Unity AI는 베타이며 기능, package version, 권한 표현과 이용 조건이 바뀔 수 있습니다. 수업 직전 설치된 버전과 공식 문서를 다시 확인합니다.

  • Unity in-Editor AI Assistant 모드 설명 ↗Ask의 읽기 전용 성격, Plan 승인, Agent 권한 수준과 project context
  • Unity Assistant Plan mode ↗Plan이 Assets/Plans에 Markdown 파일로 저장되는 동작
  • Unity 6.3 Asset metadata ↗Asset과 함께 생성되는 .meta 파일과 GUID 보존
  • Unity Assistant package 문서 ↗설치된 package에서 지원하는 모드와 동작 확인
  • Git diff 공식 문서 ↗working tree, index와 commit 사이의 변경 비교
  • Unity 6.3 SerializeField ↗private field와 Unity serialization의 관계
  • Unity AI Guiding Principles ↗AI 결과의 투명성, 데이터와 개발자 책임 원칙
